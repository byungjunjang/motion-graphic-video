4. 그 결과를 합친 초안을 검증 에이전트 4명(규칙 충돌, 사실 대조, 내부 모순, 품질 회귀·실행 가능성)이 반박했다. 지적 96건을 반영했다.

## 1. 결론

1. **엔진은 바꾸지 않는다. 부품과 규칙만 옮긴다.** 다섯 저장소 모두 "프레임은 t 의 순수 함수"라는 계약을 쓴다. 우리 렌더러는 4개 페이지가 4프레임씩 건너뛰며 나눠 찍는다(`scripts/render.mjs:48-50`). 그래서 연속 구간으로 나눠 찍는 lemo·motion-graphics 보다 상태 의존 결함이 잘 드러난다. 하지만 결과를 비교하지는 않는다. animate 는 모든 프레임을 역순으로 다시 그려 비교한다. 렌더러는 그대로 두고 이 비교 방식만 가져온다(Q-1).
2. **레퍼런스에 넣을 수 있는 것은 lemo-opuscar(59편)와 mg-styles-15(15편) 두 곳뿐이다.** 나머지 셋은 재생할 공개 영상이 없다. 이미지·GIF·WebP 만 있다. 넣어도 얇은 톤(10편 미만)이 10편을 넘는 경우는 기대값으로 없다. 실제 이득은 두 가지다. 하나는 motion-catalog 의 선택 폭이다. 다른 하나는 얇은 톤을 제안할 때의 근거다. 대신 판정·리뷰 비용이 크다. 그래서 단계적으로 넣는다(R-1·R-2, 5절 1).
3. **소리를 만드는 방법은 하나도 가져오지 않는다.** lemo 는 로컬 TTS 와 샘플 악보를 쓴다. mg-styles 와 animate 는 코드 합성 음악을 쓴다. motion-graphics 는 코드 합성과 CC0 효과음 묶음을 쓴다. 모두 R3 에 걸린다. 가져오는 것은 측정과 배치 방법뿐이다. 효과음 동기점(S-1)은 지금 손으로 하는 시각 계산을 없앤다.
4. **사람 확인 지점은 두 곳 그대로 둔다(R1).** animate 는 세 번 확인하고, motion-graphics 는 초안 검토를 한 번 더 한다. 그중 룩 확인만 기존 스토리보드 승인 화면에 싣는다(Q-5).
5. **가장 큰 효과는 공정·검수에서 나온다.** 지금 실행을 막는 장치는 두 개다. `render.mjs` 는 page error 가 나면 종료 코드 1 을 낸다. `refs.mjs board` 는 show 로 읽지 않은 후보가 있으면 멈춘다. `mix.py` 의 경고 3개는 출력만 한다. 이 제안은 글꼴 로드 실패를 막는 장치로 더한다. 결정성·글자·숫자·음량은 먼저 경고로 재고, 거짓 경고 비율을 본 뒤에 막을지 정한다.

## 3. 제안

표기는 세 가지다.
- **P1** · 바로 해도 된다. 크레딧이 들지 않고, 기존 영상을 다시 렌더·믹스해도 결과가 같다.
- **P2** · 사용자가 결정하거나, 다음 실제 영상으로 시험한 뒤 기본값으로 둘지 정한다.
- **P3** · 그 톤이나 기능을 요청받을 때만 한다.

다른 저장소의 MIT 코드를 옮길 때는 고지를 남긴다. 짧은 도우미에는 `// from <repo> (MIT, Copyright (c) 2026 <저자>)` 주석을 단다. 수십 줄 이상이면 `vendor/` 처럼 LICENSE 사본을 함께 둔다. motionmaxxing(Apache-2.0)은 look.py 만 줄여 옮기고 `scripts/look.LICENSE` 를 함께 둔다. 나머지는 방식만 따른다.

### 3-1. 레퍼런스 확장

#### R-1 [P2] lemo-opuscar 를 출처 `lo:` 로 색인한다

- **무엇** · `scripts/refs.mjs` 에 `loEntry` 를 더한다. 모양은 기존 `pmEntry/ghEntry/cvEntry` 와 같다.
  - 메타데이터는 `styleboard/catalog.json`(59행)을 쓴다.
  - 포스터는 `docs/frames/<slug>.jpg` 를 쓴다.
  - 영상은 GitHub Pages 720p(`https://lemomo-ai.github.io/lemo-opuscar/films/<slug>.mp4`)를 쓴다. HEAD 요청이 200 으로 응답하는 것을 확인했다.
  - `fetchSource` 에 `lo` 분기를 넣는다. show 를 부를 때마다 raw 주소에서 읽는다.
  - `mergeTwins` 에는 넣지 않는다. 지금 색인에 lemo 데모의 재게시가 0건이기 때문이다.
- **정렬** · 정렬의 동점 처리를 `Math.min(chars, 2000)` 으로 바꾼다(`refs.mjs:270`, `catalog.mjs:44`). 그리고 SKILL.md 2단계 1번의 `--min-chars 2000` 예시를 지운다. 이렇게 해야 긴 명세가 출처 때문에 위로 오지 않는다. 기존 165편 가운데 2000자를 넘는 21편은 서로 동점이 되어 원래 순서를 따른다.
- **전문에서 빼는 것** · `loEntry` 의 prompt 에서 두 줄을 지운다.
  - `> References (grammar only)` 인용 줄을 지운다. 이 줄에는 실존 작가·작품 이름(예 · engraving 의 Haeckel, Audubon)이 있다. 이 줄을 지우면 발췌, board 의 앞부분 보기, show 출력 모두에 그 이름이 나오지 않는다(R7).
  - `> Name:` 상표 줄을 지운다(예 · hd-2d).
  - 그 줄이 없는 3편(backrooms, city-symphony, microgame)은 처음부터 쓴다.
- **show 출력** · `show lo:<slug>` 는 STYLE.md 의 §1(본질·아닌 것), §5(모션), §6(카메라), §9(함정)와 DEMO.md 의 `## Shots` 절만 낸다(약 5천~7천 자). 우리가 가져오는 '구조·박자'는 `## Shots` 에 있다. DEMO.md 전체는 사용자가 그 항목을 고른 뒤에 `show lo:<slug> --demo` 로 읽는다. 둘 다 전체를 내면 중앙값이 약 2만 6천 자다. 그러면 2단계의 "8개 이상 읽기"에 드는 토큰이 크게 는다.
- **표기** · source 는 `lemo-opuscar (LemoLab · CC BY 4.0)`, author 는 `LemoLab`, url 은 저장소의 `styles/<slug>` 주소로 둔다.
  - board 는 meta 줄에 source 를 그대로 보여 준다.
  - catalog 는 source 를 보여 주지 않는다. 그래서 `catalog.mjs` 상세 창의 meta 에 `r.source` 를 1줄 더한다.
- **실존 IP 처리** · 기존 세 출처와 같은 기준을 쓴다. 지금 쓰는 165편에도 실존 브랜드 광고 데모가 리뷰를 통과해 있다(예 · pm:brainextends-e19ac3). 그래서 리뷰 전에 미리 빼는 것은 1편뿐이다. living-screencast 다. 이 데모의 주인공은 Clawd 이고, 따라 그리면 R6 위반이 된다. 사유는 `R6 · 실존 캐릭터` 로 적고, tone-catalog.md 의 제외 사유 목록에 한 줄 더한다. lemo 가 DEMO.md 에 'unofficial' 로 표시한 나머지 17편은 판정에 표시를 붙인다(R-3). 실제 기록 영상·데이터로 만든 것은 `실자료`, 실존 기업·제품·인물·행사가 주인공인 것은 `실존` 이다. 표시가 붙은 것을 쓸지는 리뷰에서 사용자가 정한다. hd-2d 는 label·note 에 'HD-2D' 를 쓰지 않는다.

  1. `node scripts/refs.mjs index` 출력에 `lemo-opuscar n/59` 가 나온다.
  2. 색인 항목에 `prompt` 필드가 없고, 발췌는 401자 이하다.
  3. `show lo:engraving` 출력에서 'Haeckel' 을 찾으면 0건이다.
  4. `search editorial` 상위 20개에 lo: 가 사용 비율보다 크게 몰리지 않는다.

### 3-3. 공정·검수 게이트 (확인 지점은 두 곳 그대로)

#### Q-1 [P1] render.mjs 에 글꼴 로드 검사와 결정성 비교

- **무엇**
  1. **글꼴** · 페이지를 연 뒤 선언된 글꼴을 모두 `load()` 한다. 로드되지 않은 것이 있으면 `font not loaded · <family> <weight>` 를 출력하고 종료 코드 1 을 낸다. 기존 16개 페이지의 글꼴 파일은 모두 있다. 그래서 다시 렌더해도 깨지지 않는다. 근거는 motion-graphics 의 "글꼴 전부 load 후 경고"다.
  2. **결정성** · `--snap ... --det` 일 때만 비교한다.
     - 두 번째 페이지를 열고 같은 시각을 역순으로 찍는다.
     - 비교는 ffmpeg `blend=all_mode=difference,signalstats` 의 YMAX(최대 화소 차)로 한다. 의존성은 추가하지 않는다.
     - 차가 2 이하이면 같음으로 본다(필터 GPU 오차). 3 이상이면 `결정성 · 다름 t=… 최대 차 n` 을 출력한다. 처음에는 경고만 한다.
     - 시각이 3개 미만이면 섞은 순서로 다시 찍는다.
     - 6단계 마지막 1회와 7단계 전체 렌더 직전에만 쓴다. 반복 재촬영 때마다 쓰지 않는다.
     - animate 는 같은 페이지에서 역순으로 다시 그린다. 우리는 새 페이지에서 찍는다. 첫 seek 의 시각이 임의인 경우까지 잡으려는 것이다.
  3. **WebGL** · WebGL 캔버스가 있으면 렌더러 이름(`UNMASKED_RENDERER_WEBGL`)을 한 줄 출력한다. 이 PC 에서 3D 톤 속도를 판단하는 근거다.
- **6단계 규칙** · 전환마다 전환 시각 −0.2, −0.1, 0, +0.1, +0.2 초 다섯 장을 따로 찍어 본다. ClaudeAnimationBase 는 전환마다 모든 프레임을 본다. 우리는 그것을 30fps 기준 5장으로 줄인 것이다.
- **필터를 쓰는 기존 영상** · 지금 페이지 10편이 CSS·SVG 필터를 쓴다. 그래서 경고가 날 수 있다. 이 영상들은 경고를 유지한다. 새 영상에서 T-4 를 따르는 것이 자리 잡으면 오류로 올릴지 정한다.
- **비용** · `--det` 를 쓰면 스냅 시간이 약 2배다.
- **확인**
  1. 첫 작업 영상 에서 `결정성 · 같음` 이 나온다.
  2. 복사본에 seek 밖 `let n=0; n++` 을 넣으면 `다름` 이 나온다.
  3. woff2 하나의 이름을 바꾸면 `font not loaded` 가 나온다.

#### Q-7 ② [P2 · 목표 음량을 정한 뒤] 음량 정규화

- **문제** · 2-pass loudnorm 을 linear 로만 쓰면 8편 중 6편이 성립하지 않는다. 올릴 이득에 지금 true peak 를 더하면 목표 TP 를 넘기 때문이다. 그러면 ffmpeg 는 dynamic 으로 바꾼다. dynamic 은 3초 창 AGC 다. 그래서 점입가경의 음량 상승과 "정점이 도입보다 5dB 이상" 조건(`audio-elevenlabs.md:72`)을 누른다.
  - 첫 작업 영상 · −16.77 LUFS, TP −0.25 → dynamic, 결과 −14.62
  - 3D 영상 · dynamic 인데도 결과가 −15.41 이다
- **무엇** · `mix.py` 가 오디오만 한 번 더 돌려 측정한다(`-v info`). 지금 마지막 인코드는 `-v error` 라 측정값이 출력되지 않는다. 필요한 이득은 g = −14 − I 다.
  - TP + g ≤ −1.5 이면 `volume=g` 만 곱한다(linear).
  - 그렇지 않으면 아래 두 가지 중 사용자가 고른 것을 쓴다.
    - (가) 정규화하지 않는다. "−14 로 올리려면 true peak 를 x dB 눌러야 한다"를 출력한다.
    - (나) 업샘플 true peak 리미터(`aresample=192000,alimiter,aresample=48000`)를 걸고 올린다. 꼭대기만 누르므로 곡선 모양은 거의 유지된다(측정으로 확인해야 한다).
  - 출력은 48kHz 로 고정한다.
- **적용 범위** · 기존 영상은 `video.json` 에 `loudnorm` 키가 있을 때만 적용한다. 그래야 수정 요청으로 mix.py 를 다시 돌려도 음량이 바뀌지 않는다.
- **확인**
  1. 최종 mp4 를 ebur128 로 다시 잰다.
  2. 목소리-음악 차이와 `audio-probe.py --step 2` 곡선이 바꾸기 전과 같은지 본다(리미터가 걸린 구간은 빼고 ±0.5dB).

### 3-4. 소리 (R3 안에서 · 측정과 배치만)

#### S-1 [P1] 효과음 동기점으로 손계산을 없앤다

- **문제** · 효과음 파일마다 최고점까지의 지연이 다르다(2절). 지금은 에이전트가 파일을 재고 시각을 손으로 앞당겨 적는다. 결함은 아니다. 첫 작업 영상은 맞게 놓여 있다. 하지만 영상마다 같은 계산을 반복하고, 틀리기 쉽다.
- **무엇**
  1. `audio-probe.py` 에 `--peak` 를 둔다. 첫 타격 시각과 최고점 시각을 출력한다.
  2. `video.json` 의 `sfx` 항목에 선택 4번째 칸을 받는다. 값은 `"onset"`(첫 타격), `"peak"`(최고점), 숫자(그 초) 중 하나다. 이때 시각 칸에는 화면 사건 시각을 적는다.
  3. 4번째 칸이 없으면 지금처럼 파일 시작을 그 시각에 놓는다. 그래서 기존 15편은 바뀌지 않는다.
  4. `mix.py` 는 `path, at, vol, *sync` 로 푼다. 앞당긴 시각이 0보다 작으면 파일 앞을 atrim 으로 자른다.
- **배치 규칙** · `audio-elevenlabs.md` §3 에 적는다. 두 출처의 규칙이 다르다. mg-styles 는 whoosh 최고점을 사건 시각에 맞춘다. motion-graphics 는 파일 시작을 2프레임 앞에 둔다. 그래서 우리는 이렇게 정한다.
  - whoosh 는 최고점을 전환 시각 0~2프레임 앞에 둔다. 정확한 값은 첫 영상으로 시험해 정한다.
  - 클릭은 첫 타격을 사건 1프레임 앞에 둔다. 근거는 mg-styles 08-morph `audio.py` 다.
  - riser 는 끝을 타격 시각에 둔다.
- **근거** · mg-styles `lib/audio/mgaudio/core.py`(Sound 동기점), motion-graphics `sound-effects/scripts/sound_pass.py`. 소리를 만드는 코드는 가져오지 않는다.
- **확인**
  1. 새 영상에서 시각 칸을 화면 사건 시각으로, 4번째 칸을 `"peak"` 로 적는다.
  2. `audio-probe.py --step 0.05` 로 최고점이 정한 위치 ±1프레임에 오는지 잰다. 소리는 측정값으로만 확인한다(R9).

#### S-2 [P2 · 설치 승인 뒤] whisper 를 이 PC 에서 돌게 하고, 내레이션 두 개 중 원고대로 읽은 쪽을 고른다

- **문제** · `audio-probe.py --words` 는 `whisper` 명령(openai-whisper CLI)을 찾는다. 이 PC 에는 없다.
- **무엇**
  1. **faster-whisper 로 정한다.** 무거운 의존성(ctranslate2, torch cpu, onnxruntime)은 이미 설치되어 있다. 빠진 것은 PyAV 하나다. 설치 명령은 `python -m pip install faster-whisper` 다(사용자 승인 뒤). small 모델은 약 0.5GB 를 내려받는다.
  2. faster-whisper 는 `whisper` 명령을 만들지 않는다. 그래서 `audio-probe.py --words` 분기를 고친다. CLI 대신 `faster_whisper.WhisperModel(model, device="cpu", compute_type="int8").transcribe(path, language="ko", word_timestamps=True)` 로 바꾸고, 출력은 지금과 같은 `words` 줄로 둔다(약 15줄). 안내 문구는 Mac·Windows 두 줄로 둔다.
  3. **고르기** · `audio-elevenlabs.md` §1-3 의 "두 개 중 고르기"에 전사 대조를 더한다.
     - 비교 전에 공백·문장부호를 지우고, 전사의 숫자 구간은 비교하지 않는다. 원고는 숫자를 한글 읽기로 적는데 whisper 는 아라비아 숫자로 적기 때문이다.
     - 유사도 차이가 3%p 안이면 기존 무음 기준을 따른다.
     - 숫자·고유명사가 원고와 다르거나 둘 다 유사도가 기준 미만이면, 쓰기 전에 사용자에게 알리고 다시 생성할지 묻는다. 다시 생성하면 크레딧이 든다(R4, R5).
     - 다시 생성하지 않는 것이 기본이다(`audio-elevenlabs.md:11`).
- **R3 와의 관계** · 전사는 소리 생성이 아니다. 그래서 R3 와 충돌하지 않는다. 다른 방법으로 ElevenLabs MCP 의 전사 도구(`creative_transcribe_audio`)도 있다. 다만 크레딧을 쓰고, 단어 시각을 주는지는 확인하지 못했다.
- **근거** · lemo `core/tts/asr_check.py`(한국어 글자 유사도), animate `tools/voice_words.py`(faster-whisper 단어 시각). 둘 다 통과할 때까지 다시 만든다. 우리는 고르기에만 쓴다.

#### S-3 [P3] 톤별 소리 재질

- **무엇** · 지금 기본 흐름은 모든 톤의 도입을 "패드와 피아노만"으로 둔다(`motion-rules.md:19`). `tone-catalog.md` 의 '색·질감' 칸 끝에 `소리 ·` 를 붙여 음악 프롬프트에 쓴다. 예 · 손그림은 "소리 · 어쿠스틱 기타·우쿨렐레·종이 소리", HUD 는 "소리 · 신스 펄스·짧은 비프". 새 열을 만들지 않는 이유는 Q-3 파서가 열을 헷갈리지 않게 하려는 것이다.
- **한계** · ElevenLabs 가 악기 지시를 따르는지는 측정하지 못한다. 보고에 그렇게 적는다.

#### S-4 [P3] 박자 측정 보강

- **무엇**
  - `audio-probe.py --onsets` 출력에 마디 시작(downbeat)과 저역(120Hz 아래) 비율을 더한다.
  - `--fit <전환 시각들>` 로 음악 delay(0~3초)를 찾고, 전환과 박의 오차(ms)를 출력한다.
  - 지금 "박의 정수배로 자른다"는 손계산이다.
- **근거** · animate `tools/beats.mjs`(박 위상, 마디), motion-graphics `sound_pass.py`(킥 확인, 5ms 간격 시작점 탐색).

## 5. 사용자가 정할 것

1. **새 레퍼런스를 어디까지 넣을지** · 판정(프레임 약 300장을 에이전트가 봄)과 사용자 리뷰가 크게 든다. 지난 리뷰 통과율은 23%와 61%였다.
   - (가) ms: 15편만 먼저 넣는다. 비용과 순위 영향을 잰다.
   - (나) (가) + lo: 가운데 얇은 톤·판화 계열에 해당하는 약 25편. 분석 초안의 대응 기준이다. 예 · engraving, woodcut, risograph, ink-wash, watercolor, pixel-rpg, ascii-crt, silent-film, blueprint, hologram-hud, halftone-dossier.
   - (다) lo: 58편(living-screencast 제외) + ms: 15편 전부.
   - 권장은 (나)다. 이득이 얇은 톤에 몰려 있기 때문이다.
2. **판화·인쇄 톤** · 리뷰에서 판화 계열이 살아남으면 만들지 정한다. 구현은 근사이고 난이도는 상이다.
3. **최종 음량** · 목표(−14 LUFS 권장, 유튜브·SNS 기준)와 처리 방식을 정한다. 처리 방식은 Q-7 ② 의 (가) 재기만 또는 (나) 업샘플 리미터다.
4. **whisper 설치** · `faster-whisper` 를 pip 로 설치하고 `audio-probe.py` 를 고칠지 정한다. 하지 않으면 이 PC 에서 단어 시각 맞춤과 원테이크 정거장 시각을 잴 수 없다. ElevenLabs 전사는 크레딧이 든다.
5. **Q-5·Q-6** · 다음 영상으로 시험할지 정한다. Q-5 는 승인 전 작업 시간을, Q-6 는 토큰을 늘린다.
6. **R3 유지** · CC0 효과음을 ElevenLabs 보조로 허용하면 크레딧을 아낄 수 있다. 이 제안은 R3 를 그대로 두는 것을 전제로 썼다.
7. **끝 화면** · 지금 규칙은 완전 정지다. mg-styles 는 "구도 고정 + 미세하게 살아 있는 요소 하나"를 쓴다. 이 제안은 지금 규칙을 유지한다.
